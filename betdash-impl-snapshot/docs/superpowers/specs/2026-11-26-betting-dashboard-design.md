# Локальная исследовательская платформа коэффициентов и вероятностей

Дата: 2026-11-26
Статус: черновик спецификации, ожидает одобрения пользователя

## Intent and why

Создать локальный инструмент, который помогает понять, где цена букмекера расходится с собственной оценкой вероятности, и проверять такие гипотезы честным бэктестом. Это не «предсказатель победителя» и не бот для ставок. Главная ценность — собственная история линий российских букмекеров, которой ни у кого нет в открытом доступе, и воспроизводимая оценка качества модели относительно рынка.

Причины: платные API принципиально не используются; единого легального фида на все нужные БК нет; история коэффициентов недоступна и должна накапливаться с первого запуска; пользователь хочет видеть не только вилки/value, но и статистику, тренды и оценку модели.

## Goals

- Локально (только на машине пользователя) собирать прематч-линии шести БК: Winline, Pari, Fonbet, Marathon, BetBoom, Bettery. Liga Stavok исключена по прямому указанию пользователя (доступ заблокирован WAF/IP).
- Дисциплины MVP: теннис, баскетбол, Dota 2, Counter-Strike 2. Американский футбол — расширение после MVP, не влияет на текущую схему.
- Хранить каждый опрос как immutable snapshot: `odds_snapshots`.
- Нормализовать события, участников и рынки к единому контракту.
- Построить рыночный baseline (девиго-вероятности и консенсус), рейтинговую модель (Elo/Glicko) и одну простую ML-модель после baseline.
- Делать walk-forward бэктест с контролем утечек данных и показывать набор метрик, а не одну «волшебную» цифру.
- Дать.Streamlit-витрину с экранами: Opportunity feed, Market depth, Model diagnostics, Backtest lab, Data health, Risk panel.
- Ограничить риск на уровне сигналов; автоматическое исполнение ставок не реализуется.

## Non-goals

- Платные API и подписки (SureBet, API-SPORT, BALLDONTLIE, PandaScore stats, The Odds API и т.п.).
- Liga Stavok, обход Qrator/WAF, резидентские прокси, анти-детект, работа с аккаунтами в автоматическом режиме.
- Live-модели и live-ставки в MVP.
- Автоматическая размещение ставок, props/combo/specials и нейросети в MVP.
- «Универсальная» модель на все виды спорта.
- Публикация, монетизация и передача данных третьим лицам.

## Anti-goals

- Заявить «модель побеждает рынок», если рынок использовался как признак и как benchmark без раздельной проверки.
- Счесть positive EV прибыльной ставкой без калибровки вероятности, доступной цены и поправки на лимиты/отмены.
- Возвести CLV в единственную метрику качества.
- Использовать будущую информацию в признаках или случайный train/test split.

## Constraints

- Окружение: Python 3.14, Node 26, git, без Docker, 12 ядер / 30 ГБ ОЗУ / 187 ГБ свободно. PostgreSQL, Redis, Playwright, FastAPI, Streamlit, pandas изначально отсутствуют.
- Никаких платных источников данных.
- Только публичные данные без логина; авторизованный браузер пользователя используется только для ручного осмотра, не для автоматизации.
- Лицензии: `tennis-sackmann-archive` и `tennis-data.co.uk` — некоммерческое использование с атрибуцией; данные не передаются дальше и не публикуются.
- Недокументированные эндпоинты нестабильны: адаптеры должны быть изолированы, с метриками здоровья и graceful degradation.
- Локальный характер: SQLite как primary store, DuckDB для аналитики; сервис не открывается наружу.

## Approaches

1. **Прямые открытые фиды + собственный архив (выбран).**
   Читаем публичные линии: Pari/Fonbet/Bettery через открытые JSON `/urls.json?hash=` + `/events/list`, Marathon через SSR HTML, BetBoom через публичные siteapi-роуты, Winline через публичный бинарный WebSocket. Каждый опрос пишем в `odds_snapshots`. Плюсы: бесплатно, свой уникальный архив, контроль над контрактом данных. Минусы: хрупкие недокументированные интерфейсы, Winline требует реверса бинарного протокола, BetBoom/Winline вводятся ступенчато.
2. **Модель сначала на исторических датасетах.**
   Sackmann archive, `tennis-data.co.uk`, nba_api, OpenDota, Kaggle cs2odds/FACEIT/Valve VRS. Плюсы: быстро проверить гипотезу без парсинга. Минусы: нет CLV и специфики российских линий; модель легко оторвётся от реального рынка. Используется как холодный старт признаков, не как основной путь.
3. **Короткий спайк на бесплатном OddsPapi.**
   Только Fonbet+Marathon, 250 запросов/мес, история завершённых матчей с начала 2026. Плюсы: быстрая проверка витрины. Минусы: не покрывает шесть БК и не может быть фундаментом. Не выбран.

Выбран путь №1 с использованием №2 для холодного старта признаков. Причина: только он даёт историю именно российских линий и позволяет честно измерять CLV.

## How (зафиксированные решения)

### Источники и адаптеры

- Приоритет ввода: Pari, Fonbet, Bettery (открытые JSON), Marathon (SSR HTML), BetBoom (публичный siteapi; точные роуты снимаются из сетевого лога публичной страницы), Winline (публичный WS `wss://wss.winline.ru/data_ng`, бинарный протокол).
- Адаптер — отдельный модуль с единым интерфейсом `fetch_snapshot() -> list[RawOdd]`. Адаптер никогда не меняет общую схему.
- Для каждого адаптера: TTL, backoff, таймаут, счётчики ошибок, последний успешный опрос, версия парсера.
- Никаких логинов, капч, обхода блокировок. Если страница требует ручного действия — показываем её пользователю и просим показать экран.

### Хранилище

- SQLite в WAL-режиме как единственный источник истины. Alembic-миграции.
- Таблицы: `events`, `participants`, `event_aliases`, `market_types`, `odds_snapshots`, `results`, `feature_values`, `predictions`, `model_runs`, `adapter_health`.
- `odds_snapshots` — immutable: `event_uid, bookmaker, market, outcome, odds_decimal, observed_at, source_url, adapter_version, is_live`.Никаких UPDATE/DELETE для исторических строк.
- DuckDB читает те же данные для аналитики и бэктеста; копия в Parquet при необходимости.
- Lineage: каждый признак хранит `source`, `as_of`, `transform_version`.

### Data contract

- `event_uid` — канонический ID события после нормализации; `source_event_id` — ID конкретной БК.
- Разделять `BO3/BO5`, серию и отдельную карту/сет; не смешивать их в один рынок.
- Временные метки: `observed_at` (когда цена увидена), `event_start_at`, `market_close_at`. Признак для события вычисляется только из данных строго до `observed_at` сигнала.
- Обязательные поля: `sport, league, participant_ids, market, outcome, odds_decimal, bookmaker, observed_at`.
- Запрещены: будущие линии, пост-матчевая информация в прематч-признаках, данные из аккаунта.

### Нормализация

- Реестр сущностей с алиосами и ручным подтверждением неоднозначных совпадений.
- Маппинг рынков для каждой БК в канонические: `match_winner`, `set handicap`, `total games`, `map winner`, `total maps`, `spread`, `total points`.
- Неоднозначные события получают `mapping_confidence` и не попадают в бэктест без подтверждения.

### Модели и оценка

- Рыночный prior: девиго по каждой БК и консенсус (взвешенный по исторической надёжности линии).
- Рейтинги: отдельные Elo/Glicko-2 для тенниса, баскетбола, Dota 2 и CS2. Никакой общей модели.
- Простая логистическая регрессия на признаках формы/отдыха/покрытия/патча/карты/H2H — первый ML-слой.
- CatBoost добавляется только после того, как baseline и walk-forward зафиксированы.
- Две независимые оценки: (1) качество вероятностей по факту (Brier, log-loss, calibration), (2) добавляемая ценность относительно рыночного baseline (residual, CLV). Если рынок — признак, проверка «победы над рынком» делается на отдельном дизайне с рынком только как benchmark.
- Валидация: walk-forward по времени, per-sport, с embargo; случайный split запрещён.
- Бэктест воспроизводит сигнал в момент `observed_at`, использует только доступную тогда цену и учитывает лимит/отмену как отдельные причины пропуска.
- Метрики показываются вместе: Brier, log-loss, calibration curve, CLV, ROI flat-stake, hit rate, profit by market/league, max drawdown. Порог минимального объёма выборки защищает от оптимизации по шуму.

### UX

- Opportunity feed: сигнал, модель vs рынок, confidence, время до начала, причина отсутствия цены.
- Market depth: таблица шести БК, история движения линии, девиго-вероятности.
- Model diagnostics: калибровка, residuals, feature importance, версия модели.
- Backtest lab: период, лига, рынок, стратегия, метрики, сравнение с baseline.
- Data health: пропуски, дубли, задержки, ошибки адаптеров, покрытие по БК/видам спорта.
- Risk panel: экспозиция по событию/лиге/виду спорта, дневной лимит, корреляция, kill-switch.
- Визуальный стиль: строгий аналитический интерфейс через `ui-ux-pro-max`, без «фиолетового градиента»; графики Plotly.

### Риск-слой

- signal и execution разделены; execution не реализуется.
- Лимиты: max stake на сигнал, max exposure на событие/лигу/вид спорта, max daily loss, correlation limit.
- Kill-switch при аномалиях данных (неизвестные рынки, дубли, резкие скачки без подтверждения).

### Операционка

- APScheduler внутри процесса дашборда: прематч-опрос с интервалом из `pydantic-settings`; стартово 60–120 секунд для Tier-1 адаптеров. Инкрементальное обучение запускается вместе со сборщиком и делает чекпоинты; при перезапуске продолжается с последнего состояния.
- FastAPI не нужен на старте; Streamlit владеет фоновыми потоками и читает/пишет SQLite через репозиторий, DuckDB используется для аналитики.
- Tray-апп управляет запуском/остановкой процесса и показывает статус; browser открывается по действию пользователя.
- Тесты pytest на парсинг снимков (fixtures из реальных ответов), на backtest-движок и на поток обучения/чекпоинты.
- `webapp-testing` используется позже, когда появится UI; Playwright/браузеры пока не установлены.

## Решения после ревью спецификации

Эти четыре пункта были уточнены ревьюером; я закрыл их как свои решения, исходя из уже выбранных вами источников и ограничений:

1. **Результаты для первого бэктеста.** Два трека: (A) внешние датасеты, где уже есть и коэффициенты, и результаты (`tennis-data.co.uk`, затем Sackmann/nba_api/OpenDota/Kaggle), дают холодный старт для калибровки; (B) собственные `odds_snapshots` соединяются с публичными результатами через реестр сущностей и нечёткое сопоставление по названию/дате/турниру. Трек A не заменяет B, а позволяет начать проверку гипотез до накопления истории. Сопоставление начинается с тенниса как самого чистого источника.
2. **Журнал реальных ставок.** Его нет. Все ROI/CLV в MVP помечаются как симулированные по снапшотам. Risk panel показывает «бумажную» экспозицию и лимиты, а не деньги аккаунта. Поправка на лимит/отмену учитывается как причина пропуска сигнала, а не как действие.
3. **Цена сравнения.** Основной benchmark — девиго-консенсус по доступным БК; дополнительно показывается лучшая цена. Сигнал требует минимум две БК с живой ценой; отсутствующая БК исключается из консенсуса с явным `coverage_count`. CLV считается к closing-консенсусу того же рынка; если closing-снапшот отсутствует, сделка исключается из CLV, но остаётся в остальных метриках.
4. **Запуск сборщика и обучения (правка пользователя).** При открытии дашборда поднимается один локальный процесс: Streamlit + фоновые потоки/APScheduler внутри `st.cache_resource`-синглтона. Сборщик начинает опрос сразу, обучение стартует сразу же и продолжается инкрементально, пока дашборд открыт. Чекпоинты моделей и состояние обучения пишутся на диск; при закрытии — корректная остановка. Системный демон/автозапуск ОС не требуется. Streamlit-процесс является владельцем фоновых потоков и поэтому может писать в SQLite; входящие данные идут только через адаптеры, а не из UI-форм.
5. **Трей-иконка (правка пользователя).** Локальный tray-апп (pystray + Pillow) запускает/останавливает дашборд, показывает статус адаптеров и обучения, открывает UI в браузере. Иконка — управление процессом, а не второй интерфейс; вся аналитика остаётся в Streamlit.
